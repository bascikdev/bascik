# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
Entries cover every Bascik package: `@bascik/bascik`, `create-bascik`,
`@bascik/adapter-cloudflare`, `@bascik/adapter-netlify`, `@bascik/language-server`,
the VS Code extension, and the public agent skills. A bullet names its package when
it is not `@bascik/bascik`.

## [Unreleased]

### Fixed

- While the dev server is starting, a page whose URL has a dot, such as `src/pages/release-1.0.html` at `/release-1.0` or the folder page `src/pages/v1.2/index.html` at `/v1.2`, now gets the loading page that reloads into the page once it is compiled, as every other page does. It answered `404 Not Found` until the first compile stored it, so a tab opened at `bascik` startup stayed on the 404. A missing image or stylesheet is still a 404. See [Request routing](https://bascik.dev/internals/server#request-routing-and-path-normalization).
- `bascik --build --only <page>` now writes `.bascik/<out>/ownership.json` with its pages in the same order as a full build. The file listed the same pages in a different order after a targeted build, so a tool that compares or caches build output saw a change where there was none. No change is needed in your project. See [Targeted builds](https://bascik.dev/cli#targeted-builds-only).
- The config check now rejects three mistakes it accepted. A section given a `Map`, `Date`, `RegExp`, or class instance instead of an object literal (`scoping: new Map()`) was accepted, and every setting in it was ignored; it now fails with `scoping: expected an object literal, not a Map`. A blank path (`directory.out: " "`, `directory.api: " "`, `scripts.importRoot: " "`) or a `base` of only spaces is now rejected rather than used as a folder named with a space. A `scripts.importRoot` that contains the whole project, such as `".."` or `"/"`, is now rejected: the dev server watched every file under it. A sibling folder such as `"../shared/scripts"` still works. See [Configuration Validation](https://bascik.dev/configuration#configuration-validation).
- A page that still links a stylesheet listed in `assets.inlineStyles` (or any page stylesheet with `inlineStyles: true`) is now reported. The stylesheet is inlined and not copied to `dist/`, so the `<link rel="stylesheet">` answered 404 with no warning. `bascik --build` and the dev server now print a warning naming the page and the link, and `bascik --check` reports it as `inlined-stylesheet-link`. Remove the `<link>`; the styles are already in the page. `bascik --server` also answers a missing file with a `text/plain` 404 (and 400 and 500) instead of a response with no content type. See [Inline the Global Stylesheet](https://bascik.dev/how-to/theming#inline-the-global-stylesheet).
- `pipeline.workers` now honors a number. The config check accepted `workers: 4`, but the build treated it as `true` and started one page worker per CPU core. A positive integer now turns the worker pool on with at most that many workers (still no more than there are CPU cores or pages). `true` and `false` work as before. See [Configuration](https://bascik.dev/configuration#pipeline).
- The `(N build scripts ran, M from cache)` summary after `✓ N pages transpiled` now counts the build scripts of pages that failed. With two working pages and one whose script throws, the first start of the dev server said `2 build scripts ran` though 3 ran, and the next said `0 build scripts ran, 2 from cache` though the failing script ran again. See [Performance: Output Caching](https://bascik.dev/scripts/build#performance-output-caching).
- A server, stream, build or routes script, or an API route, that throws something other than an `Error` (`throw "not found"`, `throw null`, `Promise.reject()`) is now reported as such, with the file and the line the script starts on: `The script threw the string "not found", not an Error, ...` then `in the script that starts at src/pages/s/two.html:4:1`. A server script's report named only the route (`server script error at "/s/two": Error: not found`), so it looked like an `Error` Bascik made, and an API route printed a stack of Bascik's own files. Throw `new Error("...")` to get the exact line. See [Troubleshooting](https://bascik.dev/testing/troubleshooting).
- A `data-bascik-build` or `data-bascik-routes` script that writes more than 10 MB to stdout or stderr no longer floods the terminal before its error. The 10 MB were printed first, with no newline at the end, so the `[bascik] build script error in ...` header was glued to the end of that line. None of that output is printed now, and the error says `it wrote more than 10 MB to stdout, so it was stopped and its output is not shown`. Output a script wrote without a final newline (`Loading...`) also gets one, so the next line starts on its own. Write large data to a file, or return it, instead of logging it. See [Build scripts](https://bascik.dev/scripts/build).
- Bascik no longer sends `SIGTERM` to its whole process group (the terminal job, the `npm run` or `yarn` process that started it, a test runner) when it stops while a `pipeline.exec` script with a missing `cwd` is failing to start. A typo'd `cwd` together with a stop in the same moment (a failing `parallel` script, another page error, Ctrl+C) could end the commands around Bascik. Bascik now signals only a script that has its own process ID. Fix the `cwd` to start the script.
- On macOS and Linux, `SIGQUIT` (Ctrl+\\) and `SIGUSR2` (the signal nodemon restarts with) now stop `pipeline.exec` scripts before Bascik ends, as Ctrl+C, `SIGTERM` and `SIGHUP` already did. They ended a build, the dev server, `bascik --server` or `bascik --target` dev at once and left the exec scripts running with no parent. A build or a dev boot then ends with the same signal; a running server shuts down gracefully. See [Timeouts and stopping](https://bascik.dev/exec-scripts#timeouts-and-stopping).
- Stopping the dev server (Ctrl+C, `SIGTERM`, `SIGHUP`) no longer reports the `pipeline.exec` scripts it stops as failures. A `parallel` script printed `[bascik] exec error: Error: [bascik] exec "..." exited with code null` with a stack trace, and a `post` script printed `Continuing because pipeline.onExecError is 'warn'`, while the server shut down. A script ended by a signal Bascik did not send (an out-of-memory kill) now fails with `exec "<script>" was ended by SIGKILL` instead of `exited with code null`, and a failing `parallel` script in dev prints that one line without a stack trace through Bascik's own files. See [Timeouts and stopping](https://bascik.dev/exec-scripts#timeouts-and-stopping).
- `bascik --build` and `bascik` now check that they can write the output directory and the private build folder beside it (`.bascik/dist`) before compiling anything. With a read-only `.bascik` (for example one created by `sudo` or a container), the build compiled every page and then failed with a bare `EACCES: permission denied, mkdir '.../.bascik/dist'`. It now stops at once with `[bascik] error: cannot write the private build folder ".bascik/dist" (EACCES)` and what to check. Fix the folder's ownership or permissions, or set `directory.out` to a folder you can write. See [CLI reference](https://bascik.dev/cli).
- `bascik` and `bascik --server` now explain why they cannot listen. A port below 1024 as a normal user (`--port 80`) printed Node's bare `listen EACCES: permission denied ::1:80`, with `Server startup failed:` and a stack trace in dev. It now prints `[bascik] error: permission denied to listen on localhost:80 (EACCES)` and says to use port 1024 or higher behind a reverse proxy. A `--host` (or `http.hostname`) that is not an address of this computer, which printed `listen EADDRNOTAVAIL`, now says so and lists the hosts to use instead. Both still exit with code 1. See [Configuration](https://bascik.dev/configuration#configuration-precedence).
- Removing the whole pages folder (`rm -rf src/pages`, or a branch switch that drops it) while `bascik` runs no longer prints `[bascik] watch error: OutputPathError: Refusing path outside the configured output directory` with a stack trace, twice, followed by a "pages directory does not exist" error on every rebuild. The dev server now prints one `[bascik] warning: pages folder "src/pages" (directory.pages) was removed` line, stops serving the removed pages and their static files, and builds them again when the folder comes back. Removing a folder above it (`rm -rf src`) and putting it back is noticed the same way, within a second. A file deleted while the dev server is copying it no longer prints `Failed to copy file` with a stack trace either. See [Server internals](https://bascik.dev/internals/server).
- `bascik --build` and `bascik --check` no longer fail with `EMFILE: too many open files` on a site with a few hundred pages, static assets, or components under a low open-file limit (`ulimit -n 64`, common in containers and some CI images). They opened every page source, asset, and component file at once; they now open at most 16 at a time from each thread. When a file still cannot be opened for that reason, the error names it and says to raise the limit (`ulimit -n 4096`). No change is needed in your project.
- A `bascik.config.*` whose top-level `await` waits on a promise that never settles (`await new Promise(() => {})`, or a helper module it imports that does the same) now stops with `[bascik] error: bascik.config.js never finished loading` and exit code 1. It exited with code 13 and Node's `Warning: Detected unsettled top-level await at .../@bascik/bascik/src/index.ts`, which pointed at Bascik's own file instead of your config. Make the awaited promise resolve or reject. See [Configuration](https://bascik.dev/configuration).
- `bascik --build` and `bascik --check` now fail when a component file, its companion `.css` or script, or a stylesheet that `.css` `@import`s, exists but cannot be read (for example after `chmod 000`). The build printed `warning: Failed to process` with a Node stack trace, then reported the tag as an unresolved component, shipped the literal `<my-card></my-card>`, and exited 0. It now prints one `[bascik] error: could not read component file "src/components/my-card.html"` line and exits with code 1, and `--check` reports the file instead of an unmatched tag. Fix the file's permissions, or remove it. The dev server prints the same as a warning, once, and keeps serving. See [CLI reference](https://bascik.dev/cli).
- `bascik --build` and `bascik --check` now fail when a folder inside `src/pages` or a components folder cannot be read (for example after `chmod 000`). The build printed `Failed to read subdirectory` with a Node stack trace, twice, left out every page in the folder, and exited 0. It now prints one `[bascik] error: could not read folder "src/pages/sub"` line and exits with code 1. Fix the folder's permissions, or move it out of the project. The dev server prints the same as a warning, once, and keeps serving the other pages. See [CLI reference](https://bascik.dev/cli).
- The `css-attribute-selector` and `css-is-element-names` lint rules (in `bascik --check`, the build warnings and the VS Code extension) now agree with how Bascik scopes. A selector anchored on a class that starts with a hyphen (`[data-state].-on`, `.-prose :is(h2)`) is no longer reported, because that class is scoped now. A standalone attribute selector with an `i` or `s` flag or a namespace (`[type=checkbox i]`, `[xlink|href]`) is now reported, as it leaks globally like `[data-state]`. Anchor it on a scoped class (`.card[type=checkbox i]`).

- A component's `@namespace svg url(…);` now works when another component's styles come before it on the page. Bascik joins every component's CSS into one stylesheet, and the browser ignores an `@namespace` that follows other rules, so `svg|rect {}` named an undeclared prefix and was dropped. Prefixed `@namespace` statements now move to the top of the page's component CSS, after any `@import`, and one that two components share is written once. A default namespace (`@namespace url(…);`, no prefix) stays where you wrote it, because at the top it would restrict every component's selectors; give it a prefix. No change is needed in your code; rebuild. See the "Compound / descendant element selectors" row of the [compatibility page](https://bascik.dev/compatibility).

- An attribute selector with an `i` or `s` flag or a namespace prefix in component CSS keeps its contents as written. In `a[href$=.pdf i]` Bascik scoped `.pdf` as a class and `i` as an element (`[href$=.bascik__card__pdf .b_el_card_i]`), and `a[xlink|href$=.svg]` had `.svg` scoped the same way; without the flag the value was already left alone. Browsers read an unquoted value only when it is a plain name, so quote a value that starts with `.` or `#` (`a[href$=".pdf" i]`): unquoted, the browser ignores the rule in development and production alike. Rebuild after updating. See the "Attribute selector" row of the [compatibility page](https://bascik.dev/compatibility).
- A class name that starts with a hyphen, such as `.-mt-4` (a negative margin utility) or `.--open`, is now scoped like any other class: in the component's CSS, in its `class` attributes, and in its scripts (`classList.add("--open")`, `querySelector(".-mt-4")`). It was left global on both sides, so the styles worked but applied to every element on the page with that class, and a page or another component with the same class name picked them up. The `js-document-class-query` warning now also covers such a class. No change is needed in your code; rebuild, and check any page that relied on the leaked rule. See the "Escaped or non-ASCII class name" row of the [compatibility page](https://bascik.dev/compatibility).
- A type selector with a CSS namespace prefix in component CSS (`svg|rect {}` after `@namespace svg url(http://www.w3.org/2000/svg);`, or `*|rect {}`) no longer breaks the rule. Bascik read the prefix as an element name and wrote `.b_el_<component>_svg|rect`, which browsers reject, so the rule was dropped; `ns|*` broke the same way. The type now keeps its namespace and gains the component's element class (`svg|rect.<scoped rect>`), and `ns|*` stays as written, like `*`. No change is needed in your code; rebuild. See the "Compound / descendant element selectors" row of the [compatibility page](https://bascik.dev/compatibility).
- Element selectors in component CSS written in uppercase or mixed case are now scoped wherever lowercase ones are. In `H1, H2 {}` only `H1` was scoped, so `H2` styled every `<h2>` on the page; `.card H2 {}` and `& > H2 {}` were not scoped at all; and a component with both `H1 {}` and `h1 .note {}` gave its `<h1>` elements only one of the two classes, so the other rule never matched. HTML element names are case-insensitive, so `H2`, `h2` and `<H2>` now all get the same class. No change is needed in your code; rebuild, and check any page that relied on the leaked rule. See the "Standalone element selector" row of the [compatibility page](https://bascik.dev/compatibility).
- A CSS comment left open at the end of a `<style>` block or a component's `.css` file (a `/*` with no `*/`) is now removed, as the browser ignores it to the end of that stylesheet. It was kept, and because Bascik joins a component's style blocks (and wraps one with a `media` attribute in `@media`), it hid the CSS that came after it, including the closing `}` of the `@media` rule. No change is needed in your code; rebuild, and close the comment. See the "Comments" row of the [compatibility page](https://bascik.dev/compatibility).
- A class name with an escaped quote, such as `.it\'s`, no longer breaks the component's styles. Bascik read the escaped `'` as the start of a string, so the rest of the stylesheet, up to the next quote, was not scoped and could come out with internal placeholder text in it. An escaped `/` before `*` (`.a\/*`) is no longer read as the start of a comment either. No change is needed in your code; rebuild. See the "Escaped or non-ASCII class name" row of the [compatibility page](https://bascik.dev/compatibility).
- A vendor-prefixed `@-webkit-keyframes` (or `@-moz-keyframes`) rule in a component is now scoped like `@keyframes`. Its name was left as written while `-webkit-animation: spin` was renamed, so the animation did not run in browsers that read only the prefixed rules. An `@keyframes` written in mixed case (`@KeyFrames`) is scoped too. No change is needed in your code; rebuild. See [@keyframes Scoping](https://bascik.dev/scoped-styles#keyframes-scoping).
- With `minify.css` on, the space after an escaped character in a selector is kept. `.sm\:  .b` (the class `sm:` and a descendant `.b`) minified to `.sm\:.b`, one compound selector that matched nothing, and an escaped space before a combinator (`.a\  .b`) lost the combinator. The same held for an escaped `,`, `;` or `{`. No change is needed in your code; rebuild. See the "`minify.css`" row of the [compatibility page](https://bascik.dev/compatibility).
- Comment-like text inside a CSS string that continues over a line break (a `\` at the end of the line, as in `content: "one \` followed by `/* two */ three"`) is no longer removed as a comment. The rest of the string after the line break was cut out of every build. No change is needed in your code; rebuild. See the "Comments" row of the [compatibility page](https://bascik.dev/compatibility).
- Removing a CSS comment no longer joins the values on each side of it. Every build turned `margin: 1px/**/2px` into `margin: 1px2px` and `margin: 0/* x */auto` into `margin: 0auto`, so the browser dropped the declaration, and `@media screen and/* x */(min-width: 40em)` into `and(min-width: 40em)`, which the browser reads as a function and so drops the media query. A space now takes the comment's place where the two sides would otherwise read as one value; nothing is added between selector parts such as `.a/**/.b`, where a space would change what the selector matches. No change is needed in your code; rebuild. See the "Comments" row of the [compatibility page](https://bascik.dev/compatibility).
- `@bascik/language-server` (the VS Code extension and the per-file checks of `bascik --check`) now reads `<!--` inside a component's `<style>`, `<script>`, JSON data block or `<textarea>` as that element's text, as the compiler does. Such a `<!--` hid the props and slots the template declared after it, so every page that passed them got a false `undeclared-prop` or `undeclared-slot` error. A `<script>` tag written inside a comment on a page no longer hides the slot markers after it from the `undeclared-slot` and `slot-outside-component` rules either. Update the language server or the extension; no change is needed in your code.
- A named slot marker written inside a nested component's slot wrapper (`<inner-box><span data-bascik-slot="tail"><i data-bascik-slot="extra">…</i></span></inner-box>`) or inside another named placeholder's fallback is no longer counted as a slot of the component. Bascik never fills it, but content passed for it (`<outer-c><b data-bascik-slot="extra">…</b></outer-c>`) was dropped with no build warning, no `bascik --check` finding and no `undeclared-slot` diagnostic in the editor (`@bascik/language-server`), and the literal `data-bascik-slot="extra"` attribute shipped in the page. The build and dev server now print the "does not declare" warning for it, the language server reports `undeclared-slot`, and the marker element is replaced by its own content, as an unfilled placeholder is. A usage-site wrapper written inside another wrapper (`<span data-bascik-slot="tail"><u data-bascik-slot="deep">D</u></span>`) likewise renders as its content. To fill such a slot, put the placeholder outside the nested component's tags. See [Forwarding a Slot into a Nested Component](https://bascik.dev/slots#forwarding-a-slot-into-a-nested-component).
- More of Bascik now reads `<!--` inside a `<style>`, `<script>`, JSON data block or `<textarea>` as that element's text, not as the start of an HTML comment. Before, such a `<!--` hid everything up to the next `-->` (or the end of the file):
  - In the build, `data-bascik-prop-*` receivers and `data-bascik-attr-*` bindings after a `<textarea><!--</textarea>` or a JSON block holding `"<!--"` were left unfilled, and the literal attributes shipped.
  - `bascik --check` missed the component tags after it, reporting a used component as unused and skipping a misspelled tag.
  - Request-time rendering could treat a component as renderable when its binding was not supported.
  - Build-script output after it kept its unscoped class names when rendered at request time.
  - On a page whose markup the CSP hash scan cannot follow to the end, an inline script or style holding `<!--` got no hash or the wrong hash, so the browser blocked it.

  A comment now also ends where the browser ends it (`--!>`, `<!-->`) when Bascik decides whether a usage passes content to a template with no default slot. No change is needed in your code; rebuild. See the "Raw-text comments and nested scripts" row of the [compatibility page](https://bascik.dev/compatibility).

- SVG and MathML elements with hyphenated names, `<font-face>` (and `font-face-src`, `font-face-uri`, `font-face-format`, `font-face-name`), `<missing-glyph>`, `<color-profile>` and `<annotation-xml>`, are no longer reported as missing components. HTML reserves these names for SVG and MathML, so no custom element or component can be the one meant, but the build printed `Unresolved component tag` for them and `bascik --check` listed them under "Components with no matching file", which failed `--check --strict`. Remove any `components.external` entries you added for them. See [`components.external`](https://bascik.dev/configuration#componentsexternal).
- A component tag written inside a `<![CDATA[ ... ]]>` section in SVG or MathML is no longer expanded. In `<svg><text><![CDATA[Use <book-card></book-card> here]]></text></svg>` the `<book-card>` is text the page shows, but the build replaced it with the component's markup, `bascik --check` counted it as a usage, and a `data-bascik-prop-*` receiver or `data-bascik-attr-*` binding written in such a section was filled. No change is needed in your code; rebuild. See the "SVG elements in component HTML" row of the [compatibility page](https://bascik.dev/compatibility).
- Text inside a `<![CDATA[ ... ]]>` section in a component's SVG or MathML is no longer rewritten. In `<svg><text><![CDATA[<p class="note">]]></text></svg>` the `<p>` is text, not an element, but it got the component's element and class names injected (`<p class="note b0k7...">`), and an `id` or `href="#..."` in it was renamed as if it were real markup, so the text the page showed changed. No change is needed in your code; rebuild. See the "SVG elements in component HTML" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier now treats a lone carriage return (classic Mac line endings), U+2028 LINE SEPARATOR, and U+2029 PARAGRAPH SEPARATOR as line breaks, as JavaScript does. A production build joined lines that used them into one, so `a = b\rc` became `a=b c`, which does not parse, and a `//` comment ended by one hid the rest of the script. No change is needed in your code; rebuild. See the "Semicolon-free scripts" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier no longer puts a `;` between `for` and an `await` on the next line. A production build turned `for\nawait (const x of y)` into `for;await(const x of y)`, which does not parse. No change is needed in your code; rebuild. See the "Braceless `if`/`while`/`for` body on its own line" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier now reads a `/` after the `}` of an object literal, function expression, or class expression as division. A production build read `x = {}\n/ 2 /* d */\ny()` as a regular expression `/ 2 /`, kept the comment, and joined the lines into `x={}/ 2 /*d*/y()`, which does not parse. No change is needed in your code; rebuild. See the "JavaScript literal preservation" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier now ends the statement before an `else` or `while` on the line after an object literal, function, or class that follows the `:` of a conditional, an operator such as `+` or `<`, `!`, `delete`, or an arrow. A production build turned `if (a) x = b ? {} : {}\nelse y()` into `if(a)x=b?{}:{}else y()`, which does not parse. You no longer need to end such a statement with a `;`; rebuild. See the "`else` or `while` on the line after a `}`" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier now ends the statement after an arrow function body when the next line starts with `+`, `-`, or another operator. A production build turned `x = () => {}\n+y` into `x=()=>{}+y`, which does not parse. No change is needed in your code; rebuild. See the "Semicolon-free scripts" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier now reads a block comment that spans lines as a line break, as JavaScript does. A production build turned `a = b /*\n*/ c` into `a=b c`, which does not parse, and `return /* a\n b */ x` into `return x`, which returns `x` where the source returns `undefined`. No change is needed in your code; rebuild. See the "Semicolon-free scripts" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier now keeps the statement end between `return`, `yield`, `break`, or `continue` and a template literal on the next line. A production build turned `` return\n`x` `` into `` return`x` ``, so the function returned the string where the source returns `undefined`. No change is needed in your code; rebuild. See the "Semicolon-free scripts" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier now ends a `var`, `let`, or `const` declaration at the line break after a last name with no initializer, also when an earlier name has one. A production build turned `var a = 1, b\n[x].forEach(f)` into `var a=1,b[x].forEach(f)`, which does not parse, and `let p\n+z` into `let p+z`. A line starting with `=`, `,`, `;`, `in`, or `of` still continues the declaration. No change is needed in your code; rebuild. See the "Semicolon-free scripts" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier no longer puts a `;` between a class name and an `extends` on the next line. A production build turned `class D\nextends B {}` into `class D;extends B{}`, which does not parse, so the script failed in the browser while the same code worked in development. No change is needed in your code; rebuild. See the "Declaration keyword at the end of a line" row of the [compatibility page](https://bascik.dev/compatibility).
- In the dev server, a `data-bascik-build` script that reads its page through `BASCIK_PAGE_FILE` (or `BASCIK_SOURCE_FILE`), such as a component that copies the page's `<title>`, now follows every edit to the page. After an edit the page showed its new `<title>` next to the component's output from before the edit; with `pipeline.workers: true` the first edit refreshed and later ones served the output from an earlier edit. Deleting a page and creating it again had the same effect. Builds were not affected. No change is needed in your code. See [Performance: Output Caching](https://bascik.dev/scripts/build#performance-output-caching).
- The built-in JavaScript minifier no longer joins a class field named `let`, `class`, `var`, `const`, `function`, `default`, `new`, `in`, or another keyword to the member on the next line. A production build turned `class A {\n  let\n  foo() {}\n}` into `class A{let foo(){}}`, which does not parse, so the script failed in the browser while the same code worked in development. A `static`, `get`, or `set` on a line of its own now also stays with the member after it (`static\nfoo() {}` is a static method, as in the source). No change is needed in your code; rebuild. See the "Class fields without semicolons" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier no longer puts a `;` before a `{` that sits on its own line after a function, method, class, static block, or `catch` header. A production build turned `function f(a)\n{` into `function f(a);{`, which does not parse, so the script failed in the browser while the same code worked in development. This also broke TypeScript functions with a return type written across several lines. No change is needed in your code; rebuild. See the "Semicolon-free scripts" row of the [compatibility page](https://bascik.dev/compatibility).
- `bascik` no longer hangs at full CPU when it crashes after whatever was reading its output has gone away (a closed terminal, a killed CI step, `bascik --build 2>&1 | head`). The failed write to stderr was reported to stderr again, forever, and the process never exited. It now exits with code 1 as any other crash does. See [Crash net](https://bascik.dev/internals/server#crash-net-stream-error-handling).
- The API routes page and the `bascik-scripts` agent skill no longer tell you to import a shared helper into a route file as `@/lib/db.ts`. The `@/` alias is rewritten inside `<script>` blocks only, so that import made the route answer 500 in `bascik` and `bascik --server` and stopped `bascik --build --target cloudflare` and `--target netlify`. In a file under `src/api/`, use a relative import such as `../lib/db.ts`. The server's `Failed to load API route module` error now says so when this is the cause. See [API Routes](https://bascik.dev/api-routes#file-based-routing).
- Component CSS that lists element selectors on one line now scopes every one of them when a later item takes an argument. In `h1, h2:not(.lead), li:nth-child(2) {}` only `h1` was scoped: `h2:not(.lead)` and `li:nth-child(2)` kept their bare tag names, so the rule styled matching elements on the whole page, not only in the component. A list written one selector per line (as Prettier formats it) was not affected. A class name with an escaped comma (`.cols-\[1fr\,auto\]`) is also no longer split at the comma. No change is needed in your code; rebuild, and check any page that relied on the leaked rule. See the "Comma-separated element selector list" row of the [compatibility page](https://bascik.dev/compatibility).
- `<!--` inside a component's `<style>`, `<script>`, JSON data block or `<textarea>` is no longer read as the start of an HTML comment. A CSS string such as `content: "<!--"`, a script string, or a block wrapped in `<!-- ... -->` hid everything up to the next `-->` (or the end of the file) from the compiler. Depending on where it sat, the page's stylesheet received a `BASCIK_SHIELD_0` placeholder in place of the CSS, the classes and ids after it were left unscoped while the stylesheet was scoped, the component's script lost its per-instance wrapper, or the build stopped with a "`{` is never closed" or "`<style>` is never closed" error on correct code. With `base` set, links after such a block also kept their unprefixed URLs. No change is needed in your code; rebuild. See the "Raw-text comments and nested scripts" row of the [compatibility page](https://bascik.dev/compatibility).
- `@import` text inside a CSS string in component CSS stays in the string. A rule such as `.a::before { content: "@import url(https://example.com/a.css);"; }` had the text lifted out as a real `@import` at the top of the page stylesheet, so the browser requested that URL, and the string was left empty. The same applied to an attribute selector value. No change is needed in your code; rebuild. See the `@import` row of the [compatibility page](https://bascik.dev/compatibility).
- The dev server and `bascik --server` now serve a page whose name has a dot in it at its own URL. `src/pages/release-1.0.html`, a `[version]` dynamic route with the value `v2.0`, and the folder page `src/pages/v1.2/index.html` requested as `/v1.2` all answered `404 Not Found`, because the path was read as a file with an extension, while the sitemap listed those URLs and static hosts served them. Only the `.html` and trailing-slash spellings worked. A static file with the same path is still served first. No change is needed in your pages. See [Request routing](https://bascik.dev/internals/server#request-routing-and-path-normalization).
- A component whose `data-bascik-build` script needs its page, for example one that opens `BASCIK_PAGE_FILE` to read the page's `<title>`, no longer breaks the site once any page has a server or stream script. Bascik also runs each component's build script once with no page, to prepare the component for [server scripts that return it](https://bascik.dev/scripts/server); a script that threw on that run failed `bascik --build` with `build script error ... ENOENT: no such file or directory, open ''`, and made the dev server answer 404 for every page. Such a component is now left out of request-time rendering, as any page-aware component is (`build-script-reads-page-context` on the [compatibility page](https://bascik.dev/compatibility)), and its pages build as before. No change is needed in your code.
- With `contentSecurityPolicy` set, the dev server no longer serves a freshly compiled page with a `Content-Security-Policy` header that blocks it. Opening a page while `bascik` was starting, or the live reload after editing an inline script or style, could get the new page with no hashes or with the previous version's hashes: the browser blocked every inline script and style on it, the live-reload client included, until you reloaded by hand. Builds and `bascik --server` were not affected. See [Content Security Policy](https://bascik.dev/how-to/content-security-policy).
- Saving a page the dev server cannot compile, such as a half-written page with no `<body>` yet or an empty file, now prints the page and the reason (`Build failed with 1 page error:`, then `src/pages/about.html` and `validate markup: Page does not contain a non-empty <body> element`), as starting the dev server on the same page already did. It printed `[bascik] watch error: PageProcessingError` followed by a stack trace through Bascik's own files. The dev server keeps running and serves the last good version until you save a fix, as before.
- `--config <path>` now applies to every page when `pipeline.workers` is on. Page workers ignored the flag and compiled with the defaults, or with a `bascik.config.*` in the project root, while the rest of the build used the named file: pages came out with the wrong `minify`, `base`, and `scoping` settings, and with a non-default `directory.pages` they were written to the wrong paths in `dist/`. Projects that rely on a discovered `bascik.config.*` were not affected. See [CLI reference](https://bascik.dev/cli#cli-reference).
- `bascik --build` now fails when it cannot read a page (a file without read permission, or `EMFILE` under a low open-file limit). It used to print a warning, build the rest of the site without that page, and exit 0. The page is now listed with the other page errors and the build exits with code 1. Fix the file's permissions or raise the limit (`ulimit -n`), then rebuild. The dev server still only warns, since a page can be deleted while it is being read.
- `bascik --build` no longer hides the other page errors when one page's build, routes, or server script fails. A build where one page's `data-bascik-build` script threw and another page could not be read printed only the script error and exited 1, so the unreadable page was mentioned nowhere. The summary now lists every page whose error was not already printed, as `Build failed with 2 page errors (1 printed above):`, and a routes script error is no longer printed twice. See [CLI reference](https://bascik.dev/cli).
- `bascik --build | head -1` (or `| grep -q`, or any pipe whose reader stops early) no longer stops the build halfway with `Fatal uncaught exception: Error: write EPIPE`, exit code 1 and a partly written output directory. The build now finishes and exits with the code its result deserves. A dev or production server whose log reader went away (`bascik --server | tee`, a log collector that stopped) keeps serving instead of exiting on its next log line. See [Crash net](https://bascik.dev/internals/server#crash-net-stream-error-handling).
- A `bascik.config` file whose default (or `dev`, `build`, `server`) export is a promise, such as `export default loadSettings()` with an async `loadSettings`, is now an error that names the file and the fix. Bascik used to accept it and ignore every setting in it without a message, so the site was built with the defaults. Write `export default await loadSettings()`; top-level `await` works in a config file. See [Configuration](https://bascik.dev/configuration).
- A `SIGTERM`, `SIGINT` or `SIGHUP` sent to `bascik --build`, or to `bascik` while its `pre` scripts are still running, no longer leaves `pipeline.exec` scripts running after it. Only a running server stopped them; a build that was stopped by a supervisor, `kill`, or a canceled CI step exited at once and its scripts (and whatever they started) kept running with no parent. Bascik now stops them first, then exits with the same signal as before. See [Exec scripts](https://bascik.dev/exec-scripts).
- A `data-bascik-build` or `data-bascik-routes` script no longer keeps running after Bascik is gone. When the dev server was stopped, or a build was killed, while such a script was still running, the script's process stayed behind until it finished on its own, and a script that hung stayed for good, because the 60 second limit was enforced by the process that had exited. The script now ends as soon as Bascik does. No change is needed in your scripts. See [Isolated per-script execution](https://bascik.dev/scripts/build#isolated-per-script-execution).
- The built-in JavaScript minifier no longer joins a statement to the next line when it ends in a call to a method named like a control keyword. In a script written without semicolons, a production build turned `const key = Symbol.for("app")\nconst n = 2` into `const key=Symbol.for("app")const n=2`, which does not parse; `list.with(0, 1)`, `obj.if(a)` and `$for(a)` broke the same way. In the other direction, a `switch` with a string in its header and its `{` on the next line, and a `for await (...)` with its body on the next line, got a `;` after the header. No change is needed in your code; rebuild. See the "Braceless `if`/`while`/`for` body" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier now ends the statement between an object literal or function and an `else` or `while` on the next line. In a script written without semicolons, a production build turned `if (a) x = {}\nelse y()` into `if(a)x={}else y()` and `const seen = {}\nwhile (n) step()` into `const seen={}while(n)step()`, neither of which parses; a function expression, arrow function body, or class expression before the line break broke the same way. No change is needed in your code; rebuild. See the "`else` or `while` on the line after a `}`" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier no longer puts a `;` after `var`, `let`, `const`, `function`, or `class` at the end of a line. A production build turned a declaration list that starts on the line after its keyword (`var\n  first = 1,\n  second = 2`) into `var;first=1,second=2`, which does not parse for `var` and `const` and silently made globals out of a `let` list. A private name spelled like a keyword (`this.#default`, `this.#new`, `this.#class`) at the end of a line is no longer joined to the next line either. No change is needed in your code; rebuild. See the "Declaration keyword at the end of a line" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier no longer joins two operators into a different one. A production build turned `total +\n  +extra` into `total++extra` (a syntax error), `total +\n  ++count` into `total+++count` (which runs, as `total++ + count`, and gives a different result), and a division by a regex literal such as `width / /px/.source.length` into `width //px/.source.length`, where `//` starts a comment that removes the rest of the script. A comment between the two operators had the same effect as the line break. No change is needed in your code; rebuild. See the "Operators kept apart" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier no longer ends the statement before a line that starts with `!=` or `!==`. A production build turned a comparison wrapped before its operator (`if (a.kind\n  !== b.kind)`) into `if(a.kind;!==b.kind)`, which does not parse. No change is needed in your code; rebuild. See the "Operator at the start of a line" row of the [compatibility page](https://bascik.dev/compatibility).
- The built-in JavaScript minifier now ends a class field that has no value when the next member starts with `[` or `*`. In a class written without semicolons, a production build turned `#abort\n[kResume] = null` into `#abort[kResume]=null` and `count\n*items() {}` into `count*items(){}`, neither of which parses. No change is needed in your code; rebuild. See the "Class fields without semicolons" row of the [compatibility page](https://bascik.dev/compatibility).
- HTML minification no longer changes where text ends up in a page that stops inside unfinished markup within a `<table>` (for example a file ending in `</`). The moved client scripts were placed between that markup and the text in front of it, so whitespace the browser had moved out of the table stayed inside it. No change is needed in your pages; rebuild.
- The built-in JavaScript minifier now ends a statement at a line break that JavaScript ends it at in two more places. A line after `return`, `break`, `continue`, or `yield` that starts with `-`, `+`, or a regex was joined to it, so `return\n-z` returned `-z` instead of `undefined`, and `break\n+1` did not parse. A `var`, `let`, or `const` declaration of a name with no value, followed by a line starting with `[` or `(`, was joined too (`var p\n[a, b].forEach(f)` became `var p[a,b].forEach(f)`, which does not parse). No change is needed in your code; rebuild. See the "Semicolon-free scripts" row of the [compatibility page](https://bascik.dev/compatibility).
